1. Abstract

Choosing courses each term is a decision students make with incomplete information: which course actually moves them toward the career they want, which ones conflict with their schedule, which ones they are even eligible for given their transcript. Learnix is a full-stack web application that solves this as a content-based, multi-criteria recommendation problem. Every course in the catalogue carries a skill vector across five axes — machine learning, statistics, systems, algorithms, and engineering practice — and every career target carries the same vector. Learnix scores each eligible course against a student's declared career goal, their actual transcript-derived skill level, their stated interests, their remaining prerequisite and schedule constraints, and a student-adjustable set of weights, then explains every score in plain language rather than presenting an opaque number.

Unlike collaborative-filtering recommenders that need large historical interaction data, Learnix's approach is fully explainable and cold-start-safe: a brand-new student with no history still gets ranked, reasoned recommendations from day one, and can steer the ranking logic itself by adjusting five weight sliders rather than being at the mercy of a black box.

2. Introduction & Problem Statement

Degree-program advising is typically handled by static degree-audit sheets and generic catalogue browsers that list every course but rank none of them. A student trying to decide what to take next term has to manually cross-reference their transcript against prerequisites, estimate whether a course's time slot fits their week, and guess whether a course actually serves the career they are aiming for. This is slow, error-prone, and gives no reasoning a student can inspect or challenge.

The problem Learnix addresses has four parts:

  • Relevance — which eligible courses best close the gap between a student's current skills and their career target?
  • Feasibility — which of those courses actually fit the student's remaining weekly time budget and day availability, without schedule conflicts?
  • Explainability — can the student see why a course was recommended, in terms they can evaluate and trust?
  • Steerability — can the student adjust how much each signal (goal fit, skill gap, grading history, schedule, cost) matters to them personally, rather than accepting one fixed formula?
Learnix treats these as first-class requirements rather than afterthoughts: every recommendation score decomposes into named subscores with plain-language reasons, and every subscore's weight is a value the student owns and can change at any time from Settings.

3. Objectives

  1. Design a content-based scoring model that ranks courses against a student's career-goal skill profile without requiring historical interaction data.
  2. Derive a student's current skill level purely from their confirmed academic transcript, so it can never be fabricated or go stale.
  3. Decompose every recommendation score into explainable subscores (goal fit, skill gap closed, grading history, schedule fit, cost) with plain-language reasons.
  4. Let the student steer the ranking by adjusting the relative weight of each subscore.
  5. Detect and surface real-world constraints — unmet prerequisites, schedule conflicts, weekly time-budget overruns — before a course is ever recommended.
  6. Persist every piece of student state (career goal, interests, weights, saved/hidden courses, transcript, notification settings) server-side, so the experience is consistent across devices and sessions.
  7. Build a production-shaped system: typed end-to-end, unit-tested scoring engine, a real relational schema, and a caching strategy that keeps the app responsive under real network latency.

5. System Architecture

Learnix follows a layered server-first architecture. React Server Components fetch data directly from Prisma at render time — there is no separate REST/GraphQL API layer for the main app, which removes an entire class of client/server drift bugs. State-changing operations go through typed Next.js Server Actions, which validate input with Zod, write through Prisma, and trigger targeted cache revalidation.

5.2 Request flow

A typical page request — say, opening Home — resolves the session, confirms the student has completed onboarding, then fetches the course catalogue, the student's scoring context (skills, weights, saved/hidden courses, schedule constraints) and recent notifications in parallel rather than sequentially. The scoring engine runs synchronously over that data to rank courses, and the result streams to the browser as server-rendered HTML.

7. The Recommendation Algorithm

Learnix is a content-based, multi-criteria recommender. Every course carries a skill vector across five axes (ml, stat, sys, alg, prac); every career target carries the same vector. A course's match score for a student is computed live, in three stages.

7.1 Subscores (0–99 each)

  • goals — similarity between the course's skill vector and the career target (a weighted cosine-style match), plus a small bonus if a stated interest appears in the course title or description.
  • gap — the same similarity, weighted by how far the student's current skills — derived only from confirmed transcript courses, never an invented baseline — fall short of the target. A course that closes a bigger, more-numerous skill gap scores higher than one that merely repeats a skill the student already has.
  • history — a base score, halved if a prerequisite the catalogue can check has not been confirmed on the student's transcript.
  • schedule — a base score, discounted if the course alone would consume an outsized share of the student's declared weekly time budget.
  • cost — a fixed credit-value score.

7.2 Weighted match percentage

The five subscores combine as Σ(subscore × weight) / Σweight. Weights are normalised on every read, so a student's sliders never need to sum to 100 — they can lean entirely on "goals" and "gap," or spread evenly, and the formula adapts. Three qualitative bands are shown to the student: ≥ 85 → "Great fit", ≥ 72 → "Good fit", otherwise "Okay fit."

7.3 Explanation

The top-contributing signals for a course are mapped to a plain-language reason — e.g. "It builds machine learning, which your goal needs" or "You'll need a confirmed grade in Linear Algebra, its prerequisite" — shown as the course's "why it fits you" text everywhere it appears, not just on a dedicated detail page.

7.4 Exclusion and conflicts

Hidden courses and courses that fall on a day the student has declared unavailable are removed before ranking, not scored low and left to clutter the list. Saved courses are checked pairwise for day/time overlap, so a student planning their term sees a conflict the moment it would happen, not after registering.

This entire pipeline is implemented as pure functions in lib/scoring/, independent of React or the database, and is unit-tested directly (lib/scoring/score.test.ts, 27 passing tests covering subscore formulas, ranking, band classification and conflict detection).

9. Design System

Learnix uses a desktop-first "Salt & pepper + Gothic noir" visual language — a warm off-white (#F5F4F1) background through a deep oxblood accent (#7A1F2B) — with Archivo for headings/body and Space Mono for small uppercase labels, 28px tile radii, and fully pill-shaped buttons, chips and toasts. Design tokens live in a Tailwind v4 @theme layer so every screen draws from the same palette. Entrance and ambient motion use Framer Motion, respect prefers-reduced-motion, and never hide content if a script fails to load — server-rendered content is always visible first, animation is purely additive.

10. Performance Engineering

Every data-fetching function in lib/data/repository.ts is wrapped in React's cache() so repeated calls within a single request are memoized. Catalogue data (courses, careers) and per-student data (profile, saved/hidden courses, weights, transcript, notifications) that is shared or slow-changing is additionally wrapped in Next.js's unstable_cache, giving it a short cross-request lifetime — critical because the production database is a pooled remote Postgres instance, and without this layer, screens that every page touches (like the top navigation's unread-notification count) would re-issue a network round trip on every single navigation. Every mutation (saving a course, adjusting a weight, confirming a transcript entry) calls targeted cache revalidation so the student always sees their own change immediately, never a stale cached value.

11. Testing

The scoring engine — the correctness-critical core of the system — is covered by 27 unit tests (Vitest) exercising subscore formulas, weighted ranking, band classification, exclusion filtering, and schedule-conflict detection in isolation from the database and UI. The codebase is additionally checked with strict TypeScript compilation and ESLint on every change.

12. Conclusion & Future Scope

Learnix demonstrates that a content-based recommender can be both rigorous and legible: every ranking decision traces back to a named, student-adjustable signal, and nothing is presented without a plain-language reason. By deriving skill level strictly from a confirmed transcript and letting students steer the algorithm themselves, the system avoids both the cold-start problem of collaborative filtering and the opacity of black-box ranking.

Future extensions under consideration include:

  • A greedy multi-term degree planner (prototyped in lib/data/path.ts) that sequences courses across future terms by prerequisite topology and credit/hour budget.
  • Instructor- and section-level historical grade-distribution signals, where institutional data permits.
  • Collaborative signals (e.g. "students with a similar transcript also took...") layered on top of the existing explainable base, rather than replacing it.
  • A mobile-optimized layout for on-the-go registration-period use.
